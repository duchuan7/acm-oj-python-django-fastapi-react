# 正式切换前的执行顺序与回退边界

本轮用户确认没有服务器。因此本机 5175 只部署了功能修复，
旧数据迁移、Linux 容器部署和入口切换在独立副本中演练。
不能把这套回环入口演练标为已经完成外部服务器、域名或公网正式切换。

## 已准备的本机恢复点

- 原 PostgreSQL 和 testcase 卷保持保留，旧数据库不启动；真实导出来自冷备份恢复的副本。
- 当前 Java 升级前的完整 SQL 保存在 .runtime/release/20261016-local/current-java-before-upgrade.sql。
- 该目录中的 rollback-images.json 保存升级前 API / judge / web 的 image ID。
- 独立演练各自保留冷备份、导出 JSON、MySQL dump 和摘要，目录由运行报告中的 project 定位。
- 私有文件包含密码哈希、邮箱、源码和测试内容，保持在忽略目录；不得作为公开交付物上传。

当前 Java 数据库和旧版数据库是两份不同的数据。
本轮没有把旧库覆盖到当前 Java 库，也没有把同 ID 的两份账号或提交自动合并。
正式迁移前须确定试用期间新增数据的保留与冲突映射方式，两个来源都先备份。

## 外部服务器就绪后

需要目标地址/SSH 登录配置、访问域名及可用的维护窗口，之后才有明确的部署和切换目标。

1. 检查 Linux / Docker / Compose、可用资源、磁盘、目录权限、Docker socket 与外部入口。
   按 DEPLOYMENT.md 准备独立部署目录和私有 .env，记录实际 Git commit 与镜像 ID。
2. 新目标关闭 BOOTSTRAP_ADMIN、SEED_DEMO 和自动任务，启动依赖与 API，让 Flyway 建好空库。
   初始化健康必须通过 TCP 业务账号查询，不能只判断 MySQL socket 存在。
3. 进入明确的维护窗口，阻止原入口写入并停止原评测；备份数据库和测试卷，生成一致快照。
   将目标 API / judge / web 停止，dry-run 后事务导入，只允许写空目标。
4. 核对模型及关系条数、完整字段、测试内容、密码哈希、已结束比赛榜单。
   还需验证一个真实旧账号登录；本轮用户忘记旧密码，此项未验证，也没有重置旧账号。
5. 启动目标 API / worker / web，验证四语言、注册邮件、权限、结果查询和负载。
   配置并实际验证域名与 HTTPS；数据库、队列和管理面只监听回环或内部网络。
6. 验证反向代理配置后，把维护入口切到新系统；记录切换时刻及开始接收新写入的边界。
   观察服务与队列，不删除旧卷和旧部署。

本机的 operations/rehearse.py 会自动执行其中的副本迁移、还原、短时负载和回环入口切换。
它不安装远程服务器、不修改 DNS，也不直接替换已有生产数据库。

## 回退

发生验收问题时先进入维护状态，停止新写入与新评测，保存新系统的数据库及新增业务记录。
然后把入口切回仍保留的旧服务并恢复旧评测，记录回退时刻。
单纯切回入口不等于把新系统新增记录合并回旧 PostgreSQL；后者必须另做映射与核对。

本轮的回环演练验证的是代理维护响应、旧/新 API 与页面切换、旧副本回退。
没有执行真实公网回退、切换后业务增量的反向迁移或多日运行观察。
当前使用中的 Java 服务也没有为演练而恢复成旧镜像；只保存了可定位的先前镜像恢复点。

具体运行入口见 [副本演练](../operations/README.md)，功能对照见 [功能对照](FEATURE-PARITY.md)。
