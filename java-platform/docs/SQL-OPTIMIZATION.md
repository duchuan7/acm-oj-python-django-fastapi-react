# 题目列表 N+1 统计查询优化

2026-10-21 完成。变更只针对 GET /api/problems 的逐题统计，保持分页、筛选、权限与 JSON 字段兼容。

## 问题与改动

原 ProblemService.list 查询分页题目后，对每个题目调用 view，再单独执行一次提交统计。
每页 30 题需要 30 次统计查询，已经命中索引仍需承担这些数据库往返与映射开销。

新实现只收集当前页最多 30 个题目 ID，通过绑定参数的 IN / GROUP BY 一次获取统计，
再按 ID 合并结果。不扫描题库中其他页的题目；空页跳过统计。
无提交题目保留原 submission_count=0 且省略 accepted_count 的 JSON 行为，
有提交但无 AC 时仍返回 accepted_count=0，管理权限和测试数据可见性不变。

没有新增缓存或数据库迁移。已有 submission_problem_verdict(problem_id, verdict) 覆盖统计所需列；
实际 EXPLAIN ANALYZE 显示，旧查询使用覆盖索引查找，新查询使用同一索引的范围扫描和分组聚合。
批量查询扫描的是本页所有相关记录，不能拿它的耗时直接与一条单题查询的耗时比较。

## 实测

独立项目 oj-sqlbench-c04dc3e351，固定生成 10000 题、100000 条提交记录。
这些记录由 SQL 生成，不是实际用户规模或 10 万次真实判题。
两个版本共用同一静态 MySQL 数据；应用 jar 放进相同的基线运行环境，JRE 均为 21.0.12.1。
基线镜像与 10-20 演练的 API 镜像一致；f5059b6 与 5ba1b3b 的后端源码无差异。
每个 API 限制 1 CPU / 768MiB，MySQL 限制 2 CPU / 1GiB。

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 一页 30 题的统计 SELECT 数 | 30 | 1 |
| 完整匿名列表接口 SELECT 数 | 33 | 4 |
| 空页 SELECT 数 | 3 | 3 |
| 单客户端 HTTP P50 | 25.76ms | 14.82ms |
| 单客户端 HTTP P95 | 54.85ms | 37.25ms |
| 8 客户端 HTTP P50 | 108.80ms | 87.87ms |
| 8 客户端 HTTP P95 | 289.70ms | 179.61ms |

单客户端 P95 降低约 32.1%，8 客户端 P95 降低约 38.0%。
每种客户端数量、每个版本预热后计时 320 次，合计 1280 次计时请求，无错误。
每组 4 轮、每轮每版本 80 次，交替 AB / BA 顺序；所有轮次均保留在报告中。
SQL 次数由本次 MySQL general_log 实际采集，计时前已关闭 general_log。

该数据集没有比赛，因此接口总查询数包含一次比赛公开状态检查。
实际有已结束比赛或登录用户时可能产生其他查询，不能写成所有请求固定 4 次。
这是本机热缓存、小规模并发的对比结果，存在 JVM、CPU 调度和数据库波动，不能据此推算公网吞吐上限。

## 回归与复现

- 19 项 JUnit 通过，包含分页统计、零提交、空页、搜索、难度、权限与真实 SQL 准备次数回归。
- MyBatis 测试拦截器统计实际准备的 SELECT：一页 30 题的预算为 4 次，防止逐题查询重新出现。
- 实际 MySQL 的 14 类请求完整 JSON 与旧版一致，统计值另与独立 Python fixture 计算结果比较。
- 原数据库未用于基准；测试容器及模拟数据卷已定向清理，私有配置和诊断不提交。
- 优化已部署到本机 5175 对应 API；健康、网页列表及浏览器无脚本错误检查通过，原数据和 QQ 配置保留。

从 java-platform 运行：

```powershell
python benchmarks/problem_list.py --build-images
```

脚本默认从提交 5ba1b3b 构建优化前版本，保留当前工作区。

## 可以如何描述这项工作

> 定位题目列表逐题统计导致的 N+1 查询，改为当前页 ID 批量聚合；
> 在 1 万题、10 万条模拟提交的本地 MySQL 环境中，单页统计 SQL 从 30 次降至 1 次，
> 单客户端接口 P95 从 54.85ms 降至 37.25ms，并补充查询次数及响应兼容性回归验证。
